# MyGit 更新发布操作记录

用户约定：后续需要更新 MyGit 时，由 Agent 按本文处理。用户说“发布新版 / 发布更新”时，完成检查、构建、打包和向已确定的更新仓库正常提交推送；用户只说“更新方法 / 准备更新包”时，不据此推送。不需要用户重新解释已有流程。

## 发布位置

- 使用独立 Git 仓库，根目录固定放 `latest.json` 和 `MyGit.zip`。
- 正式更新仓库地址、发布分支、本机 checkout 路径：**尚未提供**。首次正式发布时确定并补充到这里，不使用测试仓库代替。
- 应用设置入口：「设置 → 应用更新」，填写 Git HTTPS / SSH 克隆地址和分支。默认分支 `main`，以正式配置为准。
- 更新偏好存于 UserDefaults：`updateRepository`、`updateBranch`。不要在文档中记录凭据。

## 每次发布

1. 阅读本项目 `AGENTS.md`，检查当前 MyGit checkout 的工作区状态，保留用户已有修改。确认本次要发布的改动范围。
2. 核对源码 `Resources/Info.plist` 和正式仓库 `latest.json` 的版本。为本次发布选择新版本号，以及高于全部已发布版本的整数 build。不要照抄本文示例；不沿用已发布 build。
3. 将 `Resources/Info.plist` 的 `CFBundleShortVersionString`、`CFBundleVersion` 更新为本次版本，让普通构建和发布包版本保持一致；整理简短更新说明。
4. 运行 `swift test`。若包含界面改动，按 `AGENTS.md` 实际检查本次 `dist/MyGit.app`。
5. 使用与旧版相同的签名身份生成发布文件：

   ```sh
   zsh scripts/prepare-update.sh 0.1.2 3 /正式更新仓库的本机路径 '本次更新说明'
   codesign --verify dist/MyGit.app
   ```

   `0.1.2`、`3` 和路径仅为示例。脚本需要 Python 3，自动构建、打包并生成 SHA-256 清单；不执行 Git 提交或推送，也不修改源码版本。默认签名身份是 `MyGit Local Code Signing`，可通过 `MYGIT_SIGNING_IDENTITY` 指定已有证书。不要更换签名身份，否则已安装版本会拒绝更新。

6. 核对 `latest.json` 的版本、build、说明、SHA-256 与 ZIP 中 App 一致。两个文件必须来自同一次构建；不使用 Git LFS。
7. 在正式更新仓库检查状态，只暂存并提交 `latest.json` 和 `MyGit.zip`，正常推送到已确定的发布分支。不包含仓库中其他人的未提交改动，不自动强推或重写历史。源码仓库的提交、推送按当次用户要求处理。
8. 验证发布分支可读取最新清单；在应用中手动检查更新。需要实际验证替换安装时，使用测试发布仓库和可替换的构建副本，避免影响其他已安装版本。
9. 向用户报告版本号、build、更新说明、发布仓库提交哈希和验证结果；记录本次正式发布版本及位置。

## 更新机制与排查

- 应用只在用户点击时检查，使用独立临时目录浅克隆指定分支；版本清单和 ZIP 来自同一 HEAD。因此更新仓库重置历史后仍能检查。
- 用户确认后检查 SHA-256、应用标识、版本、签名和架构，再退出、替换原位置的 App 并重启；保留工程配置。Git 写操作未结束或存在其他 MyGit 实例时拒绝安装。
- 私有仓库使用本机 Git 认证，先在终端完成登录和 SSH 主机信任；应用不提供交互认证。
- 应用目录必须可写；当前包格式不支持符号链接。对外分发使用 Developer ID 签名与公证，本机自签名仅适合同机开发。
- 失败时检查 `~/Library/Logs/MyGit/update.log`；替换或打开失败会尝试恢复旧版。
- 删除旧 ZIP 再提交不会移除 Git 历史中的安装包。用户明确要求清理时，只处理独立更新仓库；重写历史和远端回收另行处理，不自动清理源码历史。
