# Grove 更新发布操作记录

用户约定：后续需要更新 Grove 时，由 Agent 按本文处理。用户说“发布新版 / 发布更新”时，完成检查、构建、打包和向已确定的更新仓库正常提交推送；用户只说“更新方法 / 准备更新包”时，不据此推送。不需要用户重新解释已有流程。

- 更新偏好存于 UserDefaults：`updateRepository`、`updateBranch`。不要在文档中记录凭据。

## 每次发布

1. 阅读本项目 `AGENTS.md`，检查当前 Grove checkout 的工作区状态，保留用户已有修改。确认本次要发布的改动范围。
2. 核对源码 `Resources/Info.plist` 和正式仓库 `latest.json` 的版本。为本次发布选择新版本号，以及高于全部已发布版本的整数 build。不要照抄本文示例；不沿用已发布 build。
3. 将 `Resources/Info.plist` 的 `CFBundleShortVersionString`、`CFBundleVersion` 更新为本次版本，让普通构建和发布包版本保持一致；整理简短更新说明。
4. 运行 `swift test`。若包含界面改动，按 `AGENTS.md` 实际检查本次 `dist/Grove.app`。
5. 使用与旧版相同的签名身份生成发布文件：

   ```sh
   zsh scripts/prepare-update.sh 0.1.2 3 /正式更新仓库的本机路径 '本次更新说明'
   codesign --verify dist/Grove.app
   ```

   `0.1.2`、`3` 和路径仅为示例。脚本需要 Python 3，自动构建、打包并生成 SHA-256 清单；不执行 Git 提交或推送，也不修改源码版本。默认签名身份是 `MyGit Local Code Signing`，可通过 `GROVE_SIGNING_IDENTITY` 指定已有证书。不要更换签名身份，否则已安装版本会拒绝更新。

6. 核对 `latest.json` 的版本、build、说明、SHA-256 与 ZIP 中 App 一致。两个文件必须来自同一次构建；不使用 Git LFS。
7. 在正式更新仓库检查状态，只暂存并提交 `latest.json` 和 `Grove.zip`，正常推送到已确定的发布分支。不包含仓库中其他人的未提交改动，不自动强推或重写历史。源码仓库的提交、推送按当次用户要求处理。
8. 验证发布分支可读取最新清单；在应用中手动检查更新。需要实际验证替换安装时，使用测试发布仓库和可替换的构建副本，避免影响其他已安装版本。
9. 向用户报告版本号、build、更新说明、发布仓库提交哈希和验证结果；记录本次正式发布版本及位置。

## 更新机制与排查

- 2026-11-03 起，正式产物名称统一为 `Grove.app`、`Grove.zip`，可执行文件为 `Grove`。Bundle ID `dev.stephenlau.mygit`、旧配置目录与签名证书保留，避免把更名识别为另一款应用。新日志位于 `~/Library/Logs/Grove/`，更名前的日志保留在 `~/Library/Logs/MyGit/`。
- 新版更新程序优先读取 `Grove.zip`；只有该文件不存在时才兼容 `MyGit.zip`。支持单个 `Grove.app` 或旧 `MyGit.app`，根据签名包的 `CFBundleExecutable` 检查架构；拒绝混装两个 App 或新包校验失败后降级读取旧包。安装仍替换当前路径，不擅自重命名用户已安装的 App。
- 旧版更新程序仅认识 `MyGit.zip` / `MyGit.app`，不能直接读取新的发布格式。首次迁移到本版本需手动安装 `Grove.app`；如果以后已有正式旧版用户，应先安排兼容过渡包再切换发布格式。当前尚未配置正式发布源，不向未知旧源推送。

- 应用只在用户点击时检查，使用独立临时目录浅克隆指定分支；版本清单和 ZIP 来自同一 HEAD。因此更新仓库重置历史后仍能检查。
- 用户确认后检查 SHA-256、应用标识、版本、签名和架构，再退出、替换原位置的 App 并重启；保留工程配置。Git 写操作未结束或存在其他 Grove 实例时拒绝安装。
- 私有仓库使用本机 Git 认证，先在终端完成登录和 SSH 主机信任；应用不提供交互认证。
- 应用目录必须可写；当前包格式不支持符号链接。对外分发使用 Developer ID 签名与公证，本机自签名仅适合同机开发。
- 失败时检查 `~/Library/Logs/Grove/update.log`；替换或打开失败会尝试恢复旧版。
- 删除旧 ZIP 再提交不会移除 Git 历史中的安装包。用户明确要求清理时，只处理独立更新仓库；重写历史和远端回收另行处理，不自动清理源码历史。
